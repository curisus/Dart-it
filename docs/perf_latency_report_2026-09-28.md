## 변경 내용

1. `company_directory.py`(신규): 해석한 회사 명단과 이름별 비교용 읽기(정규화·글자 읽기·대표 이름)를 프로세스 전체에서 1시간 보관한다. 동시 첫 요청도 한 번만 내려받고, 실패는 보관하지 않으며, API 키는 보관하지 않는다. 명단은 공개 자료라 사용자 구분 없이 공유한다.
2. 점수 계산: 결과가 쓰는 상위 20위만 정확히 고른다. 유사도 계산은 상한값이 현재 20위 점수보다 엄격히 작은 이름만 건너뛴다. 실제 명단(119,469개사)으로 검색어 2,100개를 대조해 기존 정렬과 상위 20위가 전부 같음을 확인했다(`scripts/perf/search_equivalence.py`, 불일치 0건, 순위 계산 중앙값 2.5s → 0.33s).
3. `list_report_filings`: 회사코드로 보관 명단에서 이름을 바로 찾는다(검색 재실행 없음). 빈 회사코드와 해당 보고서가 없는 회사는 이전과 같은 오류 응답을 돌려준다.
4. 키 오류 전달: 보고서 종류 확인 중 `UPSTREAM_AUTH`가 나오면 즉시 그 오류를, 모든 조회가 "자료 없음" 외의 오류로 실패하면 첫 오류를 돌려준다(명단 공유 때문에 잘못된 키가 "회사를 찾지 못함"으로 가려지지 않게).
5. 측정 도구: `ab --session-scope block`(한 프로세스가 전체 회사를 처리하는 A/B), 예정 표본 대비 완결성 검사(누락·중복·실패한 하위 실행이 있으면 FAIL).

## 검증

- 게이트: `ruff check .` 통과, `mypy --strict src tests` 통과, `pytest -v` 1,015 passed(0 failed, 0 skipped).
- 적대적 리뷰(codex): Major 1·Minor 2(모두 재현) → 전부 수정 후 게이트 재통과.
  - F1: 양쪽에서 같은 표본이 빠지면 비교기가 통과로 판정하던 기존 결함 → 예정 표본 대조 추가.
  - F0: 빈 회사코드가 입력 오류 대신 조회 오류로 바뀌던 문제 → 이전 응답 복원.
  - F2: 해당 보고서가 없는 회사에 빈 성공 결과와 잘못된 다음 단계 안내 → 이전 실패 응답 복원.
- 이전 코드와의 동작 대조(가짜 응답): 빈 값·공백·전부 빈 응답·반기보고서만 있음·정상 감사보고서는 동일. 공백이 붙은 코드·종목코드·없는 코드는 이전에도 OpenDART 단계에서 실패하던 입력으로, 오류 종류만 달라진다. 감사보고서가 전부 철회된 회사는 이전의 "빈 성공 + 다음 단계 안내" 대신 NOT_FOUND를 돌려준다(F2와 같은 원칙).

## 알려진 한계

- 1시간 안에 새로 등록되거나 이름이 바뀐 회사는 늦게 반영된다.
- 프로세스 메모리가 약 30~50MB 늘어난다(색인 약 28.5MB).
- 프로세스의 첫 검색은 명단 내려받기·해석·색인(약 4초)을 그대로 치른다. Vercel은 인스턴스가 바뀌면 그 인스턴스에서 다시 치른다.
- 잘못된 키로 보고서 종류 없이 검색하면 검색 결과는 나오고 다음 단계에서 키 오류가 난다(공개 자료라 정보 노출은 없다).
